FIX APPLIED (train_model.py):

    from sklearn.utils.class_weight import compute_class_weight

    class_weight_dict = dict(zip(unique_classes, weights))
    model.fit(..., class_weight=class_weight_dict)

RESULT:
  Still predicted wrong — class weights help but cannot compensate when
  some classes have only 5–12 samples vs 400 for others. Not enough data
  to learn from.

────────────────────────────────────────────────────────────────────────────────
STEP 8 ─ PROBLEM: IDENTICAL OUTPUT EVERY DETECTION (NOISE GATE BUG)
────────────────────────────────────────────────────────────────────────────────

After retraining with balanced data, all 3 detections returned:
  🔊 DETECTED SOUND: FIRETRUCK
  📊 CONFIDENCE: 70.08%
  All Probabilities:
    firetruck   70.08%
    train horns 18.46%
    truck horns  6.46%
    car horns    4.63%
    ...

Critically: EXACT same percentages for all 3 detections regardless of sound.

ROOT CAUSE:
  A "noise gate" in realtime_detection.py preprocess_audio() was zeroing out
  microphone input:
    noise_threshold = 0.01
    audio = np.where(np.abs(audio) < noise_threshold, 0, audio)

  Microphone recordings, after normalization to [-1,1], have many samples
  with amplitude below 0.01 — so the gate wiped out nearly all the signal,
  producing the same all-zeros (or near-zeros) MFCC features every time.
  The model consistently mapped zero features → "firetruck".

FIX APPLIED (realtime_detection.py):
  Removed the noise gate block entirely:
  REMOVED:
    noise_threshold = 0.01
    audio = np.where(np.abs(audio) < noise_threshold, 0, audio)
    max_val = np.abs(audio).max()
    if max_val > 0:
        audio = audio / max_val


────────────────────────────────────────────────────────────────────────────────
STEP 9 ─ PROBLEM: STILL IDENTICAL OUTPUT (AUDIO RECORDING BUG)
────────────────────────────────────────────────────────────────────────────────

After removing noise gate, outputs changed label to "TRUCK HORNS" but were
still identical across all recordings:
  🔊 DETECTED SOUND: TRUCK HORNS
  📊 CONFIDENCE: 46.01%
  All Probabilities:
    truck horns   46.01%
    firetruck     30.59%
    train horns   19.01%
    car horns      3.93%
    ...
  (exact same values every single recording regardless of sound played)

ROOT CAUSE:
  The original recording code in run_interactive() used sd.rec() in a loop
  inside a background thread:
    for i in range(max_chunks):
        chunk = sd.rec(chunk_size, ...)
        sd.wait()
        audio_chunks.append(chunk.flatten())

  Calling sd.rec() repeatedly from a non-main thread caused it to overwrite
  the same internal sounddevice buffer each time. Every recording returned
  the same stale audio data → same MFCC features → same prediction.

FIX APPLIED (realtime_detection.py):
  Replaced the broken sd.rec() loop with sd.InputStream using a callback:

  BEFORE (broken):
    def record_audio():
        for i in range(max_chunks):
            if stop_flag[0]: break
            chunk = sd.rec(chunk_size, samplerate=..., channels=1, dtype='float32')
            sd.wait()
            audio_chunks.append(chunk.flatten())
    record_thread = threading.Thread(target=record_audio)
    record_thread.start()

  AFTER (fixed):
    def audio_callback(indata, frames, time_info, status):
        audio_chunks.append(indata[:, 0].copy())

    stream = sd.InputStream(
        samplerate=self.sample_rate,
        channels=1,
        dtype='float32',
        blocksize=int(self.sample_rate * 0.1),
        callback=audio_callback
    )
    stop_event = threading.Event()
    with stream:
        stop_event.wait()  # blocks until user presses ENTER

  The InputStream callback runs in sounddevice's own audio thread, correctly
  capturing a fresh buffer each 100ms and appending it to audio_chunks.
